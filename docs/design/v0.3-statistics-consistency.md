# v0.3 design memo: `statistics-consistency`

*Status: deferred per issue [#13](https://github.com/seandavi/scriptorium/issues/13). Tracking label: v0.3. This memo sharpens the design questions; it does not commit to a build.*

## What's ready

- **Grounding note exists and is load-bearing.** [`knowledge/critique-techniques/statistical-inconsistency.md`](../../knowledge/critique-techniques/statistical-inconsistency.md) already covers Statcheck (Nuijten 2016), GRIM/GRIMMER (Brown & Heathers 2017; Anaya 2016), SPRITE, DEBIT, and the Carlisle baseline method, with the headline empirical numbers (50% inconsistent; 13% gross; 36/71 testable papers had a GRIM-inconsistent mean). The note also closes with the LLM-arithmetic limit, the call-out-to-script discipline, and the "Statcheck reports inconsistencies, not fraud" tone discipline.
- **Sibling skill discipline is established.** `citation-audit`'s pattern — extract candidate items, classify, emit a structured per-claim table, end with a "What this skill did NOT check" honesty section — is the obvious shape. The "honest false-negative surface" discipline is already a project convention (see citation-audit constraint 4, terminology-normalization's bibliography-exclusion count).
- **Composition target.** [`knowledge/critique-techniques/internal-consistency.md`](../../knowledge/critique-techniques/internal-consistency.md) names `statistics-consistency` as a sub-check of the broader internal-consistency audit. `reviewer-simulation`'s "statistical" lens already declares that "statcheck-style precise verification is out of scope for an LLM" and points users at this skill.

## What's missing

- **No external-tool installation pattern in scriptorium.** Today, every skill runs entirely inside the LLM. Statcheck is an R package, scrutiny is an R package, pysprite is Python. Some choice about how scriptorium ships these needs to be made (see decision point 2 below).
- **No grounding note on R-and-Python tool orchestration from LLM skills.** Scriptorium has never crossed this bridge. The decision will set precedent for future external-tool skills.
- **No vendored regex / extraction harness for APA-style NHST patterns.** Statcheck's R implementation does this; a re-implementation (Python regex over `t(48) = 2.13, p = .039` and friends) is a non-trivial parser and would need its own test fixtures. The note already flags that Statcheck's effective scope is APA-style — most biomedical reporting is not APA-style.
- **No schema slot for "extracted statistical statements"** — if the skill caches its extractions for downstream use (e.g. by `reviewer-simulation`'s statistical lens), that lives somewhere; the project hasn't decided where.

## Architectural decision points

### 1. Why NOT in-band LLM arithmetic (already settled, documented here)

Issue #13 explicitly rejects this; the grounding note explains why. Key quotes worth reflecting in the SKILL.md when written: "An LLM asked to 'verify whether F(2, 84) = 3.41 corresponds to p = 0.038' will hallucinate confidently" and "LLMs cannot reliably recompute p-values. They will get the algebra wrong, particularly for F-tests and chi-square. Always call out to a script." The supporting literature is the broader Sadasivan / Walters & Wilder line on LLM hallucination; the specific empirical claim is that LLM statistical reasoning fails at exactly the test cases (F, chi-square, p-from-test-statistic) Statcheck handles correctly. **Hard architectural rule:** never let the LLM do the arithmetic. The skill orchestrates external verification.

### 2. Vendored vs external-dependency install — the biggest open call

Three plausible postures, each with a real downside:

- **(a) Hard external dependency** — require the user to install R + statcheck + scrutiny + pysprite themselves. Most honest; sharpest install cliff. Will alienate authors who don't have an R toolchain.
- **(b) Optional dependency with graceful degradation** — skill runs, detects available tools, runs whichever checks it can, emits an explicit "could not run GRIMMER because scrutiny is not installed" line in the report. Closer to the conservative-edit / honest-about-gaps posture scriptorium already takes (matches the quartobot pattern in `citation-audit`).
- **(c) Vendored bundled scripts** — scriptorium ships a `tools/` directory with a re-implementation (Python only) of the simpler checks (GRIM at least; possibly a Statcheck-lite parser). Lower install friction; higher maintenance cost; risks divergence from the canonical implementations (and therefore the literature).

**Recommended:** (b) for v0.3. The quartobot pattern is a working precedent; the install friction is opt-in; the graceful degradation produces an honest report. (c) becomes plausible for GRIM specifically once the parser problem is solved, because GRIM is genuinely 20 lines of code.

### 3. Which tool integrates first

- **Statcheck first.** Highest yield per check (50% of papers contain at least one inconsistency); narrowest scope (APA-style NHST); existing canonical R implementation; the published validation study (Schmidt 2017) gives a calibration baseline.
- **GRIM second.** Genuinely 20 lines of arithmetic; can be vendored cleanly. The 71-of-260-papers-testable rate from Brown & Heathers means GRIM is more often N/A than diagnostic — but when it bites, it bites hard.
- **GRIMMER / SPRITE / DEBIT as bonus.** Scrutiny bundles them; if R-via-rpy2 is wired up for Statcheck, these come almost for free.
- **Carlisle is out of scope.** Corpus-level, not per-manuscript. The grounding note is explicit about this.

### 4. How to surface "this checked, this did not check" honestly

This is the false-negative danger the existing skill discipline already worries about. Concrete shapes to consider:

- Per-claim rows with `extracted_pattern`, `verification_tool`, `verification_result`. If the verification step skipped a row (e.g. GRIM not applicable because the data isn't granular), say so per row.
- A summary count of "statistical statements extracted vs verified" so the user can see the coverage at a glance.
- The "What this skill did NOT check" section calls out: non-APA reporting formats (much of biomedical), continuous-variable means (GRIM doesn't apply), the question of whether a flagged inconsistency is a transcription error vs a deeper problem, and corpus-level checks (Carlisle).

## Recommended scope cut for v0.3

Ship the **Statcheck-orchestration core** only:

1. Extract APA-style NHST patterns (`t(df) = …, p = …`; `F(df1, df2) = …, p = …`; `chi^2(df) = …, p = …`; `r(df) = …, p = …`).
2. Optionally orchestrate Statcheck via rpy2 if R is available; otherwise emit a "Statcheck not installed; install via `R -e 'install.packages(\"statcheck\")'` to enable" message and continue.
3. Emit a per-statement table with `(extracted, recomputed, discrepancy, gross_flag)`.
4. Emit the honesty section.
5. Defer GRIM/GRIMMER/SPRITE/DEBIT to a follow-on v0.4 iteration.

This keeps the install-complexity tradeoff containable, ships the highest-yield check first, and proves the external-tool-orchestration pattern before broadening it.

## Acceptance criteria

- Runs end-to-end on the Venice 2026 manuscript (or any manuscript with APA-style NHST reporting) without crashing in either the R-installed or R-not-installed configuration.
- Output conforms to the structured-markdown discipline: `# Statistics consistency`, `## Summary`, `## Per-statement assessment`, `## Patterns`, `## What this skill did NOT check`.
- Every flagged inconsistency includes the raw extracted text and a line number / section anchor so the author can navigate to the original.
- When R/Statcheck is unavailable, the skill emits the "could not run" line at the appropriate place and does not silently degrade into LLM-arithmetic guessing.
- No fabricated p-values appear in the output: every recomputed value comes from the deterministic tool, never from the LLM.
- A platform-neutral `prompt.md` exists (prompt-pack contract).
- Grounded explicitly in `statistical-inconsistency`, `internal-consistency`, `forensic-methodology`.

## Open questions for the human

- Is rpy2 acceptable as an optional dependency, or is the Python-only world worth more? (rpy2 has a real install footprint.)
- Should the skill *also* ship a `scriptorium statcheck` CLI subcommand for batch runs over a directory, or is it purely SKILL-invocation?
- Where should extracted-statistic tuples be cached, if anywhere? (Argues for or against a sidecar file separate from `MANUSCRIPT_STATE.yaml`.)
- Does the skill need a tone discipline beyond what the grounding note already supplies — i.e. how loudly does a flagged inconsistency announce itself in the output? Mirror citation-audit's "supports / partially / cannot determine" gradient, or use harder labels?
